동시 롤플레이 장애 원인 검증

작성 기준: 2026-10-02. 대상 VOC: 약 70명 동시 롤플레이의 대화 중단, AI 처리량 오류, 갑작스러운 음량 상승.

1. 결론과 판단 범위

오늘 행사 전체의 근본 원인은 아직 확정할 수 없다. 행사 시작·종료 시각과 표준 시간대, 참가자의 정확한 오류 화면, 대화 모드·기기 표본, 전체 인스턴스 로그·quota가 없다. 로그의 UTC 시각을 행사 시각으로 간주하지 않는다.

다만 다음 증거는 확보했다.

  • 최근 운영 로그에 Gemini 종료 1011 / Resource has been exhausted (e.g. check quota)가 실제 존재한다. 자원 소진 계열 오류는 확인됐지만 Live 동시 세션 quota, RPM/TPM, 프로젝트 공통 quota, 일시적인 공급자 과부하 중 무엇인지는 미확인이다. 결제 부족으로 단정하지 않는다.
  • 503 / UNAVAILABLE / The service is currently unavailable도 존재한다. 주변 요청의 기능·모델과 연결하기 전에는 이것을 Live 연결 오류로 단정하지 않는다.
  • 실제 코드로 1011 내부 오류의 fatal 오분류, 생성 중 예약 부재, 초기화 중 종료 후 orphan, 중복 연결, 재시도 동기화, terminal error 뒤 클라이언트 재접속을 재현했다.
  • 실제 재생 훅에 합성 PCM을 넣었을 때 조용한 신호 다음 큰 신호가 AGC 단계에서 클리핑된다. 브라우저 압축기의 디지털 출력도 별도 측정했다. 물리적인 스피커, Bluetooth 프로필, OS 음량, 체감 음량은 검증하지 않았다.

안전 동시 인원은 미검증이다. 70명·100명을 보장하지 않는다. 아래 모의 시험 성공률은 실제 Gemini/OpenAI 수용량이 아니다.

운영 설정·배포·키·유료 tier·quota·세션 상한·AGC 알고리즘은 변경하지 않았다. 신규 실제 사용자 녹음·전사 수집도 하지 않았다. 추가한 것은 분석 자료와 비운영 재현 시험뿐이다.

Live·요약·평가 등은 코드에서 GEMINI_API_KEY || GOOGLE_API_KEY를 우선순위로 선택한다. Cloud Run 정의는 GOOGLE_API_KEY를 매핑하지만 런타임에서 다른 키가 함께 설정됐다면 실제 선택은 다를 수 있다. 현재 운영 키가 속한 provider 프로젝트·tier·quota는 미확인이다. 비밀값, 키 일부, 해시, 인증 헤더를 보고서에 넣지 않는다. 운영자에게 비밀 관리 화면의 *변수 이름→secret 리소스/버전→provider 프로젝트 별칭* 메타데이터와 quota 화면만 요청한다. secret payload 조회 없이 소속을 입증할 수 없으면 미확인으로 둔다.

개인 음성/전사·이름·이메일·JWT·resumption handle·전체 프롬프트를 진단 일반 로그로 추가하지 않는다. 기존 로그도 민감정보가 포함될 수 있어 원본은 보고서에 복제하지 않고 최소 사건 메타데이터만 익명화했다.

완전한 타임라인의 권장 스키마

운영자의 제한된 분석 저장소에서 timestamp UTC, revision, instance_alias, conversation_alias, client_connection_seq, provider_generation, event, mode, model, error_class, close_code, attempt, latency_ms, active_count, creating_count만 남긴다. session/user ID는 행사 내 임시 익명 alias로 대체하고 별도 원본 대응표를 일반 로그에 저장하지 않는다. 전사·PCM·토큰·resumption handle은 제외한다.

create_begin → provider_connect_begin → provider_ready → first_audio/text → provider_error/close → server_retry_begin/end → client_close → client_retry_begin/end → termination(normal/abnormal) 순서를 generation별로 연결한다. 기존 비구조화 로그가 식별자 없이 출력하는 사건은 다른 세션에 억지로 연결하지 않는다.

5분 가설은 실제 infra timeout=300인 revision에서 *클라이언트 WS lifetime*이 300초 근처에 집중되는지와 upstream 종료를 대조한다. heartbeat는 request 최대 수명을 연장하는 근거가 아니다. 현재 Replit Autoscale 조회 결과만으로 Cloud Run timeout을 적용하지 않는다. Express의 30초/120초 HTTP 응답 timeout도 upgrade된 WS의 300초 근거가 아니다.

15초 가설은 플래그 시작→사용자 입력→provider 첫 audio→suppressedTurnStarted→turnComplete→강제 해제의 순서를 대조한다. 억제 경고 하나만으로 행사 과부하를 결론 내리지 않는다.

4. VOC별 장애 계층 분류

A. 대화 중단

확인된 사실: 최근 provider close와 억제 해제 경고가 있다. 앱 비활성 세션 청소는 30분/60초 주기이고, 클라이언트 close 시 provider도 닫는다. 시나리오 termination과 시간·턴 종료는 별도 정상 경로다.

재현된 결함/위험: Map 등록 전 비동기 준비로 101개 동시 생성이 모두 입장한다. 생성 중 client close 뒤에도 provider 연결이 만들어진다. 같은 논리 대화의 두 탭이 두 provider 연결을 사용한다. 같은 ID 두 생성은 Map 한 개/provider 두 개가 되어 하나가 Map cleanup 밖에 남는다(실 route ID 충돌 빈도는 미검증). 1011 내부 오류는 복구 시도 없이 종료한다. 재연결 대기 중 두 번째 close가 도착하면 세션을 삭제한다.

미확인 가설: infra/proxy timeout, 재배포/OOM/CPU/DB 지연, 실제 provider 제한, 네트워크/브라우저 suspend, 입력 VAD/EOT·출력 AudioContext 정지. 서버 응답이 없었는지, 응답은 왔으나 무음이었는지 분리해야 한다. 진행 중인 한국어 전사·iPhone 승인/Bluetooth 작업은 중복 구현하지 않았다.

B. AI 처리량 오류

확인된 사실: 최근 Resource has been exhausted와 503 UNAVAILABLE 존재. 앱 월간 토큰 quota_exceeded는 provider quota와 다른 계층이다. 앱 process 상한은 100이고 provider 제한과 관계없다.

재현된 위험: Gemini와 OpenAI reconnector 모두 1011을 fatal로 취급한다. 70개의 네트워크 close는 정확히 1,000ms 후 함께 재접속한다. 일반 HTTP retry 정책은 숫자 429/503을 4회 호출하지만 RESOURCE_EXHAUSTED 문자열을 포함하면 1회에서 멈춘다. RESOURCE_EXHAUSTED 전체를 결제 부족으로 분류하는 것은 세부 payload 없이는 과도하다. 서버가 recoverable:false 후 1000으로 닫아도 이미 대화가 시작된 클라이언트는 1,500ms 후 새 WS를 만든다. transport onopen에서 client retry count를 0으로 되돌리는 정책도 총 예산 관점에서 재검토해야 한다.

미확인 가설: 실제 tier별 동시 Live 제한, RPM/TPM, transient overload, 인증/결제/모델 권한, 같은 프로젝트에서 다른 기능의 quota 경쟁. 429·503 fake HTTP 시험은 Live SDK의 실 error payload 재현이 아니다.

C. 갑작스러운 음량 상승

확인된 사실: 기본 target RMS .15, min .5, max 4(+12.04dB), 계수 .05/.015. 훅은 PCM chunk의 RMS를 평활화하여 gain을 적용한 뒤 ±1로 hard clip한다. 이후 analyser→compressor→gain(1) 순서다. RMS estimator는 stopPlayback 때 .15로 초기화하고 작은/무음 chunk는 평활화 갱신에서 제외한다. 물리 출력 route 변경은 별개다.

재현된 위험: 합성 quiet→loud 경계에서 높은 잔류 gain과 hard clipping. 바지인·재연결의 playback reset 전후 디지털 gain 변화. compressor가 후단에 있어 이미 hard clip된 원신호는 복원하지 못한다.

미확인 가설: 운영의 AGC 값이 기본과 다른지, Bluetooth 통화/미디어 프로필 전환, OS 자체 음량/AGC, 본체 스피커 fallback, 특정 기기의 playback route. iOS/Android의 장치 열거·setSinkId 제약은 기존 작업과 연결하되 테스트 mock으로 실제 동작을 보장하지 않는다.

hold는 250ms~2시간까지 허용된다. 실제 행사 길이는 미확인으로, 20분이 행사 길이 이상이라고 주장하지 않는다. staging soak는 확인된 최대 길이+25% 이상, 해당 infra timeout을 넘기는 길이를 택한다. 이 조사에서 실행한 short-run/65초 soak는 장시간 안정성 보장이 아니다.

tests/diagnostics/voiceConcurrency.test.ts는 실제 RealtimeVoiceService/메시지 처리/reconnector를 호출하고 외부 storage·콘텐츠 준비·SDK/accounting만 mock한다. WebSocket transport도 in-process fake이므로 인증, Express upgrade, DB pool, socket/TLS, 실제 provider latency를 측정하지 않는다. Live API 비용은 없다. 입력은 생성한 16kHz PCM 100ms(3,200 bytes) frame을 25ms 간격으로 보내는 합성 스트레스 신호다. mock provider는 5ms 뒤 합성 음성을 돌려준다. 실제 말하기와 VAD/EOT 패턴 또는 provider 처리량은 아니다.

fake timers로 1011 내부 오류, 1008 인증/결제, 70 동시 retry, 중복 close를 재현하고 일반 HTTP 정책의 429/503/401/결제 소진을 별도로 검사한다. 브라우저 훅 시험은 terminal error→close→client 재접속을 직접 검증한다. 현 결함을 고쳤다고 선언하는 테스트가 아니라 *현재 동작을 고정한 characterization*이다. 이후 수정 때 기대값을 정상 동작으로 전환해야 한다.

승인 후 staging 실 provider 시험 절차 (이번에는 실행 안 함)

  • 행사와 격리된 staging URL·DB·test 계정·모델·provider 프로젝트·revision을 운영자가 확인한다. 시작 승인, 비용 상한(통화와 금액), 시간 상한, 중단 책임자를 문서화한다. 70~100 real 연결은 별도 명시 승인 없이는 시작하지 않는다.
  • test 계정 JWT는 비밀 관리 경로로만 전달하고 URL/token을 일반 로그에 저장하지 않는다. 합성 PCM/허가된 테스트 대사만 사용한다. 실제 교육 서비스나 참가자 음성은 사용하지 않는다.
  • API credential 소속의 모델별 concurrency/RPM/TPM과 결제/권한을 읽기 전용으로 확인한다. 동일 리전/revision/resource/timeout 설정을 기록한다. instance별 actual/creating와 총합을 모두 측정한다.
  • 10→30→50→70→100 각각 hold 후 drain한다. 다음 단계는 이전 단계 기준 통과와 남은 비용을 확인한 뒤에만 진행한다. 70 동시 시작과 70 동시 client/provider 재접속을 각각 시험하고 클라이언트와 서버 retry 총 호출 수를 함께 센다.
  • 최초 접속→session.ready 성공률, WS/provider 예기치 않은 종료율, user commit→첫 audio/text p50/p95, reconnect→복구 시간, 실제/생성 중 세션, CPU/RSS/loop/DB 대기, 오류 계층별 빈도 측정. response SLA와 충분한 표본 수는 시험 전에 운영자가 승인한다. retry-after를 보존하고 silent fallback을 허용하지 않는다.
  • 텍스트/TTS·emotion·per-turn 평가·요약·피드백을 행사 비율로 동시에 섞는다. Live와 같은 Gemini 프로젝트를 쓰는 경로는 RPM/TPM·CPU/DB를 함께 사용하지만 모델별 quota가 항상 동일하다고 가정하지 않는다. ElevenLabs/custom TTS와 OpenAI는 키·project가 달라 공급자 quota가 별도일 수 있으나 앱 CPU/DB는 공유한다. conversation semaphore=20, feedback=10은 process별 제한으로 Live 100과 별개다.
  • 진행 중인 전사 개선이 추가하는 STT 요청/오디오 전송도 차후 같은 mixed-load에 포함한다. 최대 실제 대화 길이 이상 hold하고 infra timeout/재배포·resume를 분리 시험한다.
  • 중단 조건: 비용/시간 상한 도달 즉시 중지, 인증/결제 오류 즉시 중지, unexpected 종료>1% 또는 성공률<99%가 한 단계에서 관측되면 확장 중지, p95가 승인 SLA를 연속 두 구간 초과, 메모리/CPU 승인 자원 여유 임계치 침범·OOM·loop 지연 지속 상승이면 중지. 해당 숫자는 시험 중단용 후보이며 운영 보장값이 아니다.
  • 신규 연결 중단→소켓 정상 drain→외부 provider 수 0 확인→test 자료 폐기. staging 승인 기준을 통과한 최대 concurrency보다 여유를 두는 운영 한도를 실측으로 결정한다. 지금은 안전 인원 숫자 미정이다.

6. 음량 시험 해석

조용한 0.02 amplitude sine 400개 chunk 뒤 0.8 sine, 무음 100개 chunk, 바지인/재연결 playback reset, mock 출력 장치 변경을 순서대로 입력했다. reset 후에는 실제 voice 훅처럼 interruption gate를 다음 응답 경계에서 해제하여 *새 PCM이 처리됐는지* 확인한다.

관측 숫자는 JSON 산출물에 포함한다. quiet steady의 gain=4, loud 직후 gain≈3.57로 AGC 후 peak=1과 clipping이 발생한다. compressor는 이미 잘린 신호를 입력받는다. 브라우저 offline 압축 후 peak/RMS는 그 디지털 그래프만 증명한다.

브라우저 압축 출력은 체크포인트 PCM을 각각 1초 반복한 독립 컨텍스트 렌더링이다. 압축기의 *서로 다른 경계 간 잔류 상태*와 여러 기기 구현 차이는 미검증이다. AGC 합성 시험의 gain/PCM 흐름은 실제 훅을 사용하며, WebAudio 렌더링에서 AGC를 다른 공식으로 재구현하지 않았다.

운영 AGC 설정값과 동일한지 미확인. 실기기 청취·OS route/volume 캡처 없이 “Bluetooth가 원인”, “compressor로 체감 음량이 해결됨”이라 주장하지 않는다. 기존 Bluetooth/iPhone 실기기 검증 결과가 제공되지 않았으므로 이 보고서에서는 미확인이다. 실기기 시험 시 테스트 PCM만 쓰고 일정한 OS 음량·출력 장치로 reset 전후 RMS/peak/gain·context state·OS route를 기록한다. 기존 출력 자동전환 알림/압축기 진단 UI는 중복 구현하지 않는다.

조건부 P1 infra timeout/자원 변경실제 timeout·CPU/메모리 병목이 확인될 때만비용·인스턴스 분산/전역 quota 영향. Cloud Run 가정 금지동일 revision 재현, 실제 길이 이상 soak·resource margin 확보비용 상한/자원·오류 악화면 이전 승인 설정으로 복귀

세션 제한을 무작정 올리거나 provider를 자동 교체하는 안은 제시하지 않는다. 기존 평가 기준·사용자 점수는 변경하지 않는다. 미확인 행사 증거 확보와 staging 승인 전에는 서비스가 “70명에 안전하다”는 운영 안내를 하지 않는다.
