# 6. Dependency Direction은 한 단계 더 확장해야 합니다

현재:

> Route → Service → Storage → Schema

는 좋습니다.

하지만 이것만 검사하면 **현재 구조에서 중요한 Provider 경계가 빠질 수 있습니다.**

저라면 Expected Layer를 이렇게 정의합니다.

```text
Client
  ↓
API Boundary
  ↓
Application / Service
  ↓
Domain Logic
  ↓
Storage
  ↓
Schema
```

그리고 외부 의존성은:

```text
Application / Service
        ↓
Provider Abstraction
        ↓
Gemini / OpenAI / Custom Provider
```

입니다.

즉 Dependency Direction 표에 최소한 다음을 넣으세요.

```text
Client → API
API → Service
Service → Domain Logic
Service → Storage
Storage → Schema
Service → Provider Abstraction
Provider Abstraction → Provider SDK
```

그리고:

```text
Service → Provider SDK
Domain → Provider SDK
Client → Provider SDK
```

같은 것이 발견되면 **Provider Leakage**로 표시.

# 7. "Provider Leakage = Critical"은 좋지만 한 가지 조심해야 합니다

현재:

> Provider Leakage is explicitly called out as a Critical item.

이건 좋습니다.

하지만 **실제로 provider SDK를 직접 호출하는 것이 항상 Critical은 아닙니다.**

예를 들어:

```text
providers/openaiProvider.ts
```

안에서 OpenAI SDK를 직접 사용하는 것은 정상입니다.

반면:

```text
evaluationEngine.ts
   ↓
@google/generative-ai
```

처럼 Domain Service가 직접 SDK를 호출한다면 문제가 됩니다.

따라서 문서에는:

> Provider SDK usage inside the designated provider adapter is expected and is not considered leakage.

라는 규칙을 넣으세요.

그리고:

> Leakage means provider SDK dependency escaping the provider abstraction boundary.

라고 정의하면 됩니다.

가 훨씬 안전합니다.

**"실패 = 환경 문제"라고 단정하지 않는 것이 중요합니다.**
