전체적으로 **방향은 맞습니다.** 오히려 지금 단계에서 `#1273`을 먼저 하는 것은 좋은 판단입니다.
다만 지금 명세 그대로 실행하면 **“현재 구조를 잘 기록한 문서”는 나오지만, 다음 단계인 Platformization / Actor abstraction / AI Agent Evaluation 설계를 위한 dependency map으로는 4~5가지가 부족합니다.**

제가 보기에는 **약 80점짜리 계획**입니다. 아래를 보완하면 95점 수준이 됩니다.

## 1. 가장 중요한 보완: "현재 구조"와 "확장 시 경계"를 분리

현재 명세는 거의 전부:

> "무엇이 어디에 연결되어 있는가?"

를 조사합니다.

그런데 우리가 이 문서를 만드는 목적은 단순 문서화가 아니라 **RoleplayBot을 Human → AI Agent → Robot으로 확장할 때 어디를 추상화해야 하는지 찾는 것**입니다.

따라서 각 domain에 다음을 추가하세요.

```text
Current responsibility
Current dependencies
Inbound dependencies
Outbound dependencies

Extension risk
Future abstraction candidate
```

예를 들어 Persona라면:

```text
Persona

Current responsibility:
- AI 상대역의 성격/행동 정의

Inbound:
- Scenario
- Session
- Simulation

Outbound:
- AI Service
- Prompt Builder
- Avatar

Extension risk:
- Persona가 HUMAN/AI Agent/Robot을 구분하는 책임을 갖고 있는지

Future abstraction candidate:
- Actor / Agent definition
```

이게 이번 작업의 **가장 중요한 추가사항**입니다.

### 추가 권장

```text

```

특히 **Actor**가 중요합니다.

앞서 이야기한:

```text

AI Agent
Robot
Simulator
```

을 앞으로 하나의 추상화 계층으로 만들 가능성이 높기 때문입니다.

다만 지금 실제 코드를 변경하라는 뜻이 아닙니다.

문서에:

> **Future Domain / Candidate Abstraction**

으로만 기록하세요.

# 3. 특히 "Actor"를 별도로 추적하세요

현재 구조를 조사하면서 이런 질문을 반드시 던져야 합니다.

> **현재 코드에서 "사용자", "AI Persona", "Agent", "Simulator"가 암묵적으로 동일한 개념으로 취급되는 곳은 어디인가?**

예를 들어:

```text

 ↓
```

```text

   ↕

   ↕
```

따라서 dependency-map에 별도 표를 추가하는 게 좋습니다.

| Simulator       | ...   | SimulationActor    |

이 표 하나가 향후 아키텍처 설계에서 굉장히 중요합니다.

# 7. "Model Provider" dependency를 반드시 추가

현재 코드에:

* `aiService`
* `aiServiceFactory`
* Gemini
* OpenAI Realtime
* TTS
* video generation

등이 있기 때문에 앞으로 굉장히 중요합니다.

현재:

```text
Application
 ↓
AI Service
 ↓
Provider
```

인지,

```text
Route
 ↓
Gemini/OpenAI
```

처럼 직접 연결된 곳이 있는지를 찾아야 합니다.

그리고 문서에:

> **Provider leakage**

라는 항목을 넣으세요.

### 위험

특정 도메인이 Gemini/OpenAI SDK에 직접 의존하면 AI Agent/Robot 확장 시 교체 비용 증가.

### Safe-change rule

> Domain layer must depend on provider abstraction, not provider SDK directly.

현재 코드에 이미 `aiServiceFactory`가 있으므로 이 부분이 특히 중요합니다.

# 8. API는 Domain으로 보기보다 "Boundary"로 보는 게 좋습니다

현재 9개 domain 중 `API`는 성격이 조금 다릅니다.

실제로는:

```text
API
 ├── HTTP
 ├── WebSocket
 ├── Agent API
 └── OpenAPI
```

라는 **외부 경계 계층**입니다.

따라서 dependency-map에서:

> API Domain

이라고 부르기보다:

> **API Boundary**

로 정의하는 것을 추천합니다.

그리고 다음을 구분하세요.

```text
Internal API
External API
Realtime API
Agent API
Admin API
```

특히 향후 AI Agent Evaluation에서는 외부 Agent가 들어오는 구조가 중요합니다.

# 13. "Dependency Direction"을 추가하세요

단순히:

> A → B

만 기록하지 말고 **허용 방향**과 **실제 방향**을 비교하세요.

예:

```text
Route
 ↓
Service
 ↓
Storage
 ↓
Schema
```

가 정상인데,

```text
Service
 ↓
Route
```

가 발견되면 architecture violation 후보입니다.

표:

| From    | To      | Actual | Expected | Risk     |
| ------- | ------- | ------ | -------- | -------- |
| Service | Route   | direct | ❌        | High     |
| Route   | Service | direct | ✅        | Low      |
| Client  | DB      | direct | ❌        | Critical |

이것이 향후 리팩토링 우선순위를 결정하는 데 매우 유용합니다.
