# Task: Implement ContentX → RoleplayX Assessment Content Publishing Integration v1

## Objective

Implement the first production-safe integration boundary between ContentX and RoleplayX.

ContentX is the canonical Assessment Content Factory.

RoleplayX is the Assessment Runtime and Evaluation Platform.

Do NOT merge the two systems.
Do NOT redesign the existing RoleplayX Scenario model.
Do NOT rewrite the existing assessment/evaluation runtime.

The goal is to allow an AssessmentScenarioPackage generated and published by ContentX to be imported into RoleplayX and executed using the existing RoleplayX Assessment/Roleplay/Evaluation pipeline.

---

## Architecture

```text
ContentX
  Assessment Package
       |
       | AssessmentScenarioPackage v1
       v
RoleplayX Content Import Layer
       |
       v
Existing RoleplayX Scenario Registry
       |
       v
Existing Assessment Runtime
       |
       v
Employee <-> AI Persona
       |
       v
Existing Evaluation / Feedback
```

ContentX remains the canonical authoring source.

RoleplayX stores a published runtime representation.

---

## Phase 1: Contract

Create a versioned contract:

`AssessmentScenarioPackage v1`

The contract must contain:

* schemaVersion
* package metadata
* assessment metadata
* competencies
* scenarios
* scenario context
* objectives
* successCriteria
* personas
* difficulty
* flowGraph
* personaSwitchRules
* playerConstraints
* evaluation configuration
* terminationRules
* simulationHarness
* analyticsSpec
* ContentX source identity
* ContentX content version
* publication timestamp

Use Zod for runtime validation.

Do not use `any` where the existing project has a concrete type available.

---

## Phase 2: RoleplayX Import API

Add a dedicated Content Import service.

Suggested endpoints:

POST /api/content/import/validate

POST /api/content/import

The validate endpoint must perform validation without creating database records.

The import endpoint must:

1. Validate the package.
2. Validate organization/tenant access.
3. Validate category mapping.
4. Map ContentX scenario data to the existing RoleplayX `scenarios` schema.
5. Preserve ContentX source metadata.
6. Create or update the published scenario deterministically.
7. Return the imported package and scenario IDs.

Do not bypass existing authorization middleware.

Respect existing organization isolation.

---

## Phase 5: Versioning

ContentX content versions must be immutable once published.

Example:

ContentX:
Team Leader Promotion Assessment v1.0

RoleplayX:
Scenario linked to ContentX v1.0

Later:

ContentX:
Team Leader Promotion Assessment v1.1

RoleplayX must create a new published version rather than silently changing the historical v1.0 assessment.

Existing assessment results must continue to reference the exact scenario/rubric/evaluation context used during execution.

Do not break the existing feedback snapshot mechanism.

---

## Phase 6: Idempotency

Repeated import of the same:

contentxPackageId + contentxVersion

must NOT create duplicate scenarios.

Implement deterministic upsert behavior.

Different ContentX versions must remain independently addressable.

---

Do NOT:

* create a second runtime Scenario model
* rewrite the evaluation engine

## Acceptance Criteria

The implementation is complete when this exact flow works:

```text
ContentX Assessment Package
        ↓
AssessmentScenarioPackage v1
        ↓
RoleplayX /api/content/import/validate
        ↓
VALID
        ↓
RoleplayX /api/content/import
        ↓
Scenario Registry
        ↓
Create Assessment
        ↓
Assign Employee
        ↓
Employee performs Roleplay
        ↓
Existing AI Persona Runtime
        ↓
Existing Evaluation
        ↓
Existing Feedback Report
```

The integration must not require modifications to the existing runtime behavior except where necessary to consume the imported Scenario.

Before modifying code, inspect the current repository structure, schema definitions, API routing conventions, authentication/organization middleware, Assessment creation flow, Scenario CRUD, and evaluation pipeline.

Reuse existing project patterns rather than introducing new architectural conventions.
