---
name: 자동 충돌 병합 검증
description: 자동 병합 결과에서 충돌 표시 밖의 선언 중복까지 확인해야 하는 이유
---

충돌 표시 제거만으로 자동 병합 결과를 정상으로 간주하지 않는다.

**Why:** 자동 병합의 충돌 표시는 모든 의미적·구문적 결함의 목록이 아니다. 표시 밖의 선언 중복도 검사해야 기존 기능과 새 동작을 안전하게 보존할 수 있다.

**How to apply:** 병합을 계속하기 전에 타입 검사와 영향을 받은 테스트를 실행한다. 기존 화면 변경과 새 동작을 함께 보존하고, 한쪽 파일 전체 선택으로 다른 작업을 지우지 않는다.

병합 후 프런트 HMR 갱신을 서버 코드 반영의 증거로 간주하지 않는다.

**Why:** 이 프로젝트에서는 병합으로 브라우저 코드만 갱신되고 실행 중인 Express 프로세스가 이전 라우터 요청 계약을 계속 사용한 사례가 있다. 파일이 올바르고 테스트가 통과해도 실행 중인 조합은 불일치할 수 있다.

**How to apply:** 서버 파일 변경 후 프로세스 시작 시각과 병합 시각을 대조한다. 수정 적용 시 관리형 애플리케이션 워크플로를 한 번 재시작하고, 기존 생성 결과 불명확 세션은 재시작만으로 해소됐다고 간주하지 않는다.

외부 GitHub PR 충돌을 API로 해결할 때는 최신 main을 다시 읽고, 그 트리 위에 승인된 변경만 적용한다. 예상한 ref가 달라지면 쓰기 전에 멈춰 새 변경을 확인한다.

**Why:** PR을 순차 병합하는 동안 별도 작업이나 게시 커밋이 main에 추가될 수 있다. 오래된 PR 트리 전체를 병합 결과로 사용하면 충돌 파일과 무관한 새 파일도 잃을 수 있다.

**How to apply:** 양쪽 부모를 보존하는 병합 커밋과 비강제 ref 갱신을 사용하고, 최종 main에서 두 수정 및 동시 작업의 보존을 확인한다.
